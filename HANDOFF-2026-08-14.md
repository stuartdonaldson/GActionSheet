### 2. Findings from the raw capture (AC #1/#2)

- Structure lives under `document.tabs[0].documentTab` (not top-level
  `document`) because `includeTabsContent: true` was used.
- **6 inline images** confirmed:
  `inlineObjectProperties.embeddedObject.imageProperties.{contentUri,
  cropProperties}`, `.size.{height,width}` (PT), `.description` (currently
  Docs' auto-placeholder text like `"page1image38953456"` — this is the field
  §19.3's write-back proposal would target).
- **1 genuine positioned/floating image** found
  (`positionedObjectProperties.positioning.layout: WRAP_TEXT`). **This
  contradicts §19.3's "no identified example in the source documents yet"
  justification for deferring positioned-object support** — the deferral
  needs re-examination, not treatment as safe.
- **Box/table-cell finding (contradicts §19.3's structural assumption):**
  the blue-background box pattern in this doc is **paragraph-level shading**
  (`paragraphStyle.shading.backgroundColor` = RGB(0.812, 0.886, 0.953),
  Google Docs' standard light-blue), appearing in 175 contiguous paragraphs —
  **not a 1-cell table** (`grep` for `table` in this doc's body content:
  zero matches). §19.3 currently claims "a box is, structurally, a table
  cell" and that fixing `processTable_`'s image-walk covers it automatically
  — that's wrong for this document. A box built as plain shaded-paragraph
  content still needs paragraph-level image handling, independent of table
  handling.
  - **Caveat:** this was checked against doc `1zQkR...`, not specifically
    against Church Policy 05 (the doc the bead names for the box pattern).
    Worth a second capture against that doc to confirm the pattern holds
    there too, or to find a genuine table-based box if one exists elsewhere.

### 3. Follow-up spike: docx export / comment anchors / revision history

User asked a design question mid-session: given the goal is LLM ingestion,
would downloading the doc as `.docx` (instead of the JSON) get real comment
anchors and revision history that the Docs-API-JSON path doesn't have? This
matters because `gts-6ls9` (comment-position spike, same source doc) already
found the Drive Comments API `anchor` field to be a confirmed dead end —
opaque `kix.<token>` IDs, zero positional structure, 57/57 comments with
`quoted_text: null`.

Extended `src/SPIKE-CommentPosition.js` (existing inert-until-enabled spike
pattern, `SPIKE_COMMENT_POSITION_ENABLED`) with two new ops, temporarily
flipped the flag to `true`, deployed, ran both live, flipped back to `false`
and redeployed (confirmed inert again — `unauthorized`/routing error on a
follow-up call):

- **`docx_export_probe`** (`_spikeCpDocxExportProbe`) — exports the doc via
  `Drive.files.export` (OOXML mimetype), unzips with `Utilities.unzip`
  (built into GAS, no library needed — the `Blob` must have
  `.setContentType('application/zip')` set first, otherwise `Utilities.unzip`
  throws `Invalid argument: ContentType`), and regex-scans
  `word/document.xml` / `word/comments.xml`.
  - **Result: 62 `commentRangeStart`/`commentRangeEnd`/`commentReference`
    triplets**, and the first one **wraps real document text** (`<w:t>ORGANIZATIONAL
    CHART</w:t>` inside the range). This is a real, position-encoded anchor
    tied to an actual run — confirms the user's hypothesis that docx export
    solves the exact problem the Drive Comments API can't. Count differs
    slightly from Drive's 57 (62 vs 57) — worth reconciling (deleted
    comments? replies counted separately?) before relying on it, but the
    mechanism itself is real and live-verified on this doc.
- **`revision_history_probe`** (`_spikeCpRevisionHistoryProbe`) — lists
  `Drive.files.revisions` for the doc.
  - **Result: 3 revisions, all with `exportLinks`** (fetchable), all
    `keepForever: false` (subject to Google's default retention window —
    don't assume deep history is always available, only recent).

Neither op has been written up in `docs/procedure-exporter.md` yet — that's
open work (see Next steps).

## Architecture discussion (not yet actioned)

User is considering: extract images → LLM-analyze each → cache the
description (skip re-analysis unless the image changed) → merge into the
LLM-ingestion JSON artifact; needs an Anthropic API key + HTTP/SDK access;
asked for a survey of what's available in GAS vs local Python for docx
parsing, image extraction, caching, and LLM API access. Answered in-session
(not written to a doc) — summary of the recommendation, worth carrying
forward if this direction gets picked up:

- **DOCX/XML parsing**: GAS has `Utilities.unzip` + `XmlService.parse`
  (built-in, proven this session) — no new library needed. Local Python
  already has `python-docx` in `pyproject.toml`; for comment-range XML
  specifically, stdlib `zipfile` + `xml.etree.ElementTree` is enough (avoid
  relying on python-docx's weak native comment support).
- **Image extraction**: already proven via the plain JSON path
  (`contentUri` → `UrlFetchApp.fetch` → Drive file), no new library.
- **Caching**: `CacheService` (100KB/value, 6h max TTL) and
  `PropertiesService` (9KB/value, 500KB total) are both **too small** for a
  growing image→description index — don't use either. Recommended: a
  Drive-hosted JSON index keyed by content hash
  (`Utilities.computeDigest`/`hashlib.sha256`), same append-only-ledger
  convention as `deployment-ledger/test.jsonl`.
- **Secrets**: extend `local.settings.json` with `anthropicApiKey` (same
  pattern as `webappSecret`/`adminSecret`/`axiomQueryToken`); GAS side via
  `PropertiesService.getScriptProperties()` (same as `WEBAPP_SECRET`).
- **LLM API access**: local Python **must use the official `anthropic` SDK**
  (not raw `requests` — this project's Python side already prefers sanctioned
  wrappers, and the SDK is the mandated default per the `claude-api` skill).
  GAS has **no official SDK** — raw `UrlFetchApp` against
  `https://api.anthropic.com/v1/messages` is the correct (only) option there,
  vision content block shape: `{"type":"image","source":{"type":"base64",
  "media_type":..., "data":...}}`.
- **Recommended split**: keep LLM calls **out of GAS** (6-min execution cap,
  no SDK) — GAS does export + hash + cache-check only; a local Python script
  (new `scripts/call_anthropic.py`, following the `call_webapp.py`/
  `query_axiom.py` wrapper convention) does the actual vision-analysis calls
  and cache writes.
