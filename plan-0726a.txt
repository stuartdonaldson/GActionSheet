--------------------------------------------------------------------------------
THE ONE THING THAT DRIVES THIS ORDER
--------------------------------------------------------------------------------
Everything downstream is waiting on ONE gate: the human review of View A that
freezes the AC (ADR-0013). Until it happens, .4.3's projection, .4.14's contract,
and both hardening beads are all guessing. So the plan is organised to reach that
review in the first sitting, not the fifth.

The old bead graph made that impossible — .4.7 depended on .4.3 and .4.5, i.e.
"the UI needs the endpoint." That is false for a perceptual oracle. Both edges
are now removed and .4.7 is READY.

Why it's false: the review asks "does the list read well, do the filters feel
right, does tier-gating of the sync and edit controls read correctly." None of
that needs a GIS round trip — it needs REAL DATA, delivered statically. A live
verified capture is not cheap right now (NUUC-Dispatch's GIS spike routes are
decommissioned, ND-z0l), but the data is reachable under the existing
WEBAPP_SECRET gate with no identity plumbing at all.

DO NOT fabricate the fixture. An earlier draft of this plan proposed capturing
`list_importable_actions` (open-only, excludes the current doc) and hand-adding a
few resolved rows for the Closed/All states. That is unsafe here, because
isResolved() (SyncManager.js:2272) matches FREE-TEXT SYNONYMS, not an enum:

    delegated: delegated routed forwarded escalated handed-off transferred
    closed:    done complete finished closed resolved finalized
    (also in-progress: active working running…; waiting: blocked on-hold stalled…)

Real status values are arbitrary user-typed strings collapsing into semantic
buckets. A fabricated fixture would hold 'Open' and 'Closed' and nothing else,
and the review would freeze an AC blind to how the status column reads with a
dozen literal values meaning three things — exactly the perceptual property the
review exists to judge. Fabrication would hide the finding.

Instead: take gts-79dw.4.11 SLICE 1 first (see G1a). Extract the parameterized
reader, expose it through one TEST_TOKEN-gated capture route, and capture real
rows for every filter state. One deploy cycle, one time; page iteration stays
pure-static afterwards. The work is not throwaway — it is .4.11's core, pulled
forward to where its regression test (the existing Import tab suite) is cheapest.

Remaining honest caveat: tier is a mode switch in the mockup (render as VIEW / as
EDIT / as the assignee) rather than a real resolution. That one is fine — which
is why the expensive multi-folder ACL fixture (.4.16) is NOT on the critical path
to this review.

    rules, to a surface that cannot call the function.
    Fixing the matching in one place also fixed it for real: _matchesState now
    normalizes separators, so canonical 'In Progress' lands in the InProgress
    bucket (it previously matched nothing, since the synonym list spells it
    'in-progress'). Same fix now applies to the sheet and the sidebar too.
    Real vocabulary caveat for the review: the captured statuses are Open /
    In Progress / Done only — no delegated-bucket value (forwarded, escalated)
    exists in the live data, so that rendering is judged from the fixture's
    vocabulary block, not from a row.
    Extract _readTeamActions(teamId, opts) from _listImportableActionsData;
    re-point _listImportableActionsData at it with opts reproducing today's
    behaviour exactly (list_importable_actions stays byte-identical — enforced by
    tests/test_import.py and scn/contract.py, so the regression proof is free);
    expose the parameterized reader via ONE TEST_TOKEN-gated capture route. Do
    not add filter params to the production list_importable_actions contract just
    to serve a fixture.

    the window boundary. Page scaffolding for .4.7 can start in parallel — only
    the capture waits on this.

  console work — split rather than block a code session on a console tab.
