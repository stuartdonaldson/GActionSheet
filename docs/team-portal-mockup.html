What this mockup is (read before reviewing)

  • Every row is real captured data from docs/team-portal-fixture.json — statuses, assignees and document names are what the teams actually typed. Never hand-edit that file; re-capture with scripts/capture_team_actions_fixture.py.
  • Each row arrives already carrying the server's getStatusDisplay() answer for its status — bucket, resolved, icon. This page re-derives nothing, so it cannot disagree with the sheet or the sidebar about what a status means.
  • Access tier is a mode switch here, not a real resolution: choose VIEW or EDIT to see how the sync and edit affordances read at each. A NONE-tier caller never reaches this page.
  • Read paths are wired; writes are inert. Sync, edit and status change only report what they would call — they land in gts-79dw.4.14 against the AC frozen at this review.
  • The window ages out resolved rows only — an open action is never hidden by it, however long since it was touched. Decided at the 2026-07-27 review gate: that is the frozen behaviour, not an accident — a stale open action never ages out at any window setting (plan §12.1).
  • Team is a real control, decided at the same gate: one page, an in-page switcher over the teams the verified caller resolves (R21, plan §12.3). Signed in as and Access stay simulation-only.
  • Status × Mine is composed from two real server results (the status filter's rows intersected with the caller's own rows); the backend applies both in one query.
  • Not present in the captured data: any delegated-bucket status (forwarded / escalated / routed). The three buckets that do appear are Open, In Progress and Closed.
